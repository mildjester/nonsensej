Running WordPress Behind a Reverse Proxy

posted: 2019-10-15

Wordpress
Apache

Environment

Apache 2.2.34

When the main site runs on Server A (www.sample.com) and WordPress runs on Server B (sub.sample.com),
we’ll use an Apache reverse proxy to make them accessible as follows.

Main site: https://www.sample.com/
WordPress: https://www.sample.com/blog

Note that other reverse proxies are already configured, so we’ll set this up to affect them as little as possible.
Other pages (Server C): https://www.sample.com/media

■Server A Configuration

Apache Configuration

Configure the reverse proxy in httpd.conf or similar as follows.
Wrap it in a Location block so it doesn’t affect the other reverse proxies.

<Location "/blog">
    ProxyPass http://sub.sample.com/blog
    ProxyPassReverse http://sub.sample.com/blog
    ProxyPassReverseCookieDomain sub.sample.com www.sample.com
    ProxyPassReverseCookiePath / /blog/
</Location>

Access under /blog will now be forwarded to Server B (sub.sample.com).

■Server B Configuration

Apache Configuration

The Apache configuration can simply be written assuming requests come to sub.sample.com.
Create a blog directory under the DocumentRoot and put the WordPress source there.

Treating Requests as SSL

The WordPress pages themselves will now display, but the URLs of required external files such as JS/CSS/images become non-SSL,
which causes errors in browsers like Chrome.
So add the following to .htaccess to force requests to be treated as SSL.

SetEnv HTTPS on

*Note
You might ask what happens when http://sample.com/blog is accessed without SSL,
but non-SSL pages are not recommended in the first place, so I haven’t considered that here.
If a request comes to http://sample.com/blog, redirect it to https://sample.com/blog.
If you really need to accept both non-SSL and SSL, take measures such as setting “X-Forwarded-HTTPS: on” in the reverse proxy for SSL connections.
With a setup like “External -> (HTTPS) -> ELB -> (HTTP) -> Server A -> (HTTP) -> Server B”, it gets quite cumbersome.

Correcting the Host Name

With the steps so far, $_SERVER['HTTP_HOST'] and $_SERVER['SERVER_NAME'] remain sub.sample.com.
Pages seem to display fine, but warnings appear in the browser console on the admin screen, which is annoying, so let’s fix it.

Add the following at the top of wp-config.php.

if (isset($_SERVER['HTTP_X_FORWARDED_HOST']) && $_SERVER['HTTP_X_FORWARDED_HOST'] === 'www.sample.com') {
    $_SERVER['HTTP_HOST'] = 'www.sample.com';
    $_SERVER['SERVER_NAME'] = 'www.sample.com';
}

Now the host name is rewritten for requests forwarded by the reverse proxy from www.sample.com.
(There may be a better way, but this approach works for now.)
