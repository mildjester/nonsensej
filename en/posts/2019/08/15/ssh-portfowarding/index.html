Accessing External Servers from Local Using SSH Port Forwarding

posted: 2019-08-15

Docker

Environment

  • amazonlinux:2017.03-with-sources
    • The base image of the Docker container.
    • It’s assumed that the SSH client software is installed with yum.

Goal

I wanted an application running in my local environment (Docker)
to access API servers and DB servers that have access restrictions,
so I achieved this using SSH port forwarding.

With SSH port forwarding, traffic you receive on a specific port can be relayed to another server via a specific server (which you must be able to SSH into).
Run the command as follows.

ssh -f -N -L {local port to listen on}:{IP or host name of the server to access}:{port of the server to access} -i {path to the SSH private key} {SSH user}@{SSH server} -p {SSH port} -4

(The ssh options are easy to look up, so I’ll skip explaining them.)

For example, the following command means
Traffic received on my port 10080 is forwarded via server2 to port 80 on server1, and the response is returned as-is to the requester.
Here, server2 is assumed to accept SSH connections as ec2-user on port 22 (private key authentication).

ssh -f -N -L 10080:server1:80 -i ~/.ssh/id_rsa ec2-user@server2 -p 22 -4

Steps

(1) Using plain port forwarding

The traffic flow looks like the diagram below.

  • SSH port forwarding is run in the web app container.
  • When the web app sends traffic to its own port 3306, port forwarding kicks in
    and it accesses db.server.com:3306 via ssh.server.com.
  • When the web app sends traffic to its own port 10443, port forwarding kicks in
    and it accesses api.server.com:443 via ssh.server.com.

Run the SSH port forwarding command inside the Docker container where the web app runs.

ssh -f -N -L 3306:db.server.com:3306  -L 10443:api.server.com:443  -i /path/to/secret_key user@ssh.server.com -p 22 -4

Then change the following in the application, and access will go through port forwarding.
・Change connections to “db.server.com:3306” to connect to “localhost:3306”
・Change connections to “api.server.com:443” to connect to “localhost:10443”

(2) Port forwarding via a bastion container

If the application changes in (1) are difficult, for example because they are hard-coded in the source code,
use this procedure instead.

The traffic flow looks like the diagram below.

  • SSH port forwarding is run in the bastion container.
  • When the web app sends traffic to port 3306 on the bastion container, port forwarding kicks in
    and it accesses db.server.com:3306 via ssh.server.com.
  • When the web app sends traffic to port 443 on the bastion container, port forwarding kicks in
    and it accesses api.server.com:443 via ssh.server.com.

Create a dedicated Docker container as the bastion, and have it run the SSH port forwarding command as the container’s command.
*The f option is removed so that the process doesn’t go to the background.

ssh -N -L 0.0.0.0:3306:db.server.com:3306 -L 0.0.0.0:443:api.server.com:443 -i /path/to/secret_key user@ssh.server.com -p 22 -4

Then, in the hosts file of the container running the web app,
map “db.server.com” and “api.server.com” to the bastion container’s IP address.
You can find the bastion container’s IP address with the following command.

nslookup {bastion container name} | grep Address | tail -n +2 | cut -f2 -d ' '

As a shell script, it looks like this.

#!/bin/bash -eu

HUMIDAI_IP=`nslookup humidai | grep Address | tail -n +2 | cut -f2 -d ' '`
echo "${HUMIDAI_IP}	db.server.com" >> /etc/hosts
echo "${HUMIDAI_IP}	api.server.com" >> /etc/hosts

This completes the setup for communication using SSH port forwarding.

Note

If the only server you want to reach via port forwarding is the DB server,
you can run the command from step (1) and then, as in (2), add a hosts entry pointing db.server.com to 127.0.0.1 (itself).

However, if you want to forward traffic on the same port the web app uses (443), as with the API server,
you can’t have SSH port forwarding listen on a port the web app is already using,
so a bastion container like the one in step (2) is required.
