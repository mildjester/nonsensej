Investigating Input Events with IME Enabled

posted: 2019-04-10

javascript

Input events with IME enabled differed quite a bit between PC, Android, and iOS, so I looked into them.
The test environments were as follows.

OS Browser
PC (Linux Mint 19.1 MATE) Chrome Ver.73.0
Android 8.0.0 (Galaxy S8) Chrome Ver.73.0
iOS 12.2 (iPhone 6) Safari 12.1

I checked the events fired when typing into a text box.
The events I checked were keydown, keyup, keypress, textInput, and input.

(On Android, the keyboard app may also have an effect, not just the browser?)

IME Enabled: While Typing (Uncommitted)

Events fired while typing hiragana one character at a time.

Event PC Android iOS Value obtained
keydown ○ ○ String before this input
keyup ○ ○ ○ *Differs by OS
keypress ○ String before this input
textInput
input ○ ○ String after this input

*The value obtained in keyup was as follows.
PC: The previously committed string
Smartphones: The string after this input

On Android, for some reason the events above fired twice from the second character onward.
Moreover, in the second round, even keydown returned the string after this input.

IME Enabled: On Commit

Events fired when committing the typed text.
On a PC, that’s when you press the Enter key.

Note that on smartphones, a commit happens even when typing half-width alphanumerics,
and the behavior was the same as below.

Event PC Android iOS Value obtained
keydown ○ ○ *Differs by OS
keyup ○ String after this commit
keypress
textInput ○ ○ ○ *Differs by OS
input ○ ○ ○ String after this commit

*The value obtained in keydown was as follows.
PC: The previously committed string
Android: The string after this commit

*The value obtained in textInput was as follows.
PC, iOS: The previously committed string
Android: The string after this commit

On iOS, for some reason the input event fires three times.
Moreover, one of them returned the previously committed string,
and the other two returned the string after this commit.

IME Disabled: On Input

Events fired when typing half-width alphanumerics etc. with IME disabled.
Smartphones have no concept of IME, so the results are the same as with IME enabled.
However, the issue of Android events firing twice does not occur.

Event PC Android iOS Value obtained
keydown ○ ○ ○ String before input
keyup ○ ○ ○ String after input
keypress ○ ○ String before input
textInput ○ String before input
input ○ ○ ○ String after input

On Character Deletion

Events fired when deleting characters with Backspace or Delete.
There seem to be no differences between OSes here.

Event PC Android iOS Value obtained
keydown ○ ○ ○ String before deletion
keyup ○ ○ ○ String after deletion
keypress
textInput
input ○ ○ ○ String after deletion

Events on Cutting Text

Events fired when cutting text via right-click on a PC or long-press on a smartphone.
There seem to be no differences between OSes here either.

Note that cutting text with Ctrl+x on a PC
behaved the same as character deletion.
(Probably because both are character deletions via key input.)

Event PC Android iOS Value obtained
keydown
keyup
keypress
textInput
input ○ ○ ○ String after deletion

Events on Pasting Text

Events fired when pasting text via right-click on a PC
or long-press on a smartphone.
There seem to be no differences between OSes here either.

Event PC Android iOS Value obtained
keydown
keyup
keypress
textInput ○ ○ ○ String before pasting
input ○ ○ ○ String after pasting

Pasting with Ctrl+v on a PC gave the following.

Event PC Value obtained
keydown ○ String before pasting
keyup ○ String after pasting
keypress
textInput ○ String before pasting
input ○ String after pasting

Summary

If you’re building a responsive site, it may be safer not to hook into events that behave differently across OSes.
If you do use them, you’re likely to run into trouble unless you fully understand the differences.

The value obtained is sometimes the state before an operation and sometimes after,
but I suspect you can get the post-operation state in all cases by making good use of setTimeout.
